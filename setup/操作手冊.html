第 2 步　建立自己的 Cloudflare 服務

登入 Cloudflare

本人操作：先在瀏覽器登入自己的 Cloudflare。Agent 執行：需同意：

npx wrangler login       # 瀏覽器出現確認頁：核對帳號與權限後，由你本人按允許
npx wrangler whoami      # 顯示 Account ID → 填入 設定.json 的 account_id

建立空白 D1

npx wrangler d1 create ai-secretary-progress
# 可選：加 --location apac。輸出的 database_id → 填入 設定.json 的 d1_database_id
node tools\prepare.mjs                # 產生工作副本；第一次一定是 DAILY_ENABLED=false、crons=[]
node tools\d1-init.mjs --check        # 只檢查：三份檔案只含 CREATE TABLE IF NOT EXISTS
node tools\d1-init.mjs                # 依序匯入 schema.sql → mail-deliveries.sql → production.sql

三份都是空白表格結構，沒有任何待辦或示範資料。重跑安全：已存在的表格不會被改動。

第一次部署，排程保持關閉

node tools\deploy.mjs --check         # 列出將部署到哪個帳戶、哪個 D1；不連網
node tools\deploy.mjs                 # 對外：部署 Worker

Wrangler 會顯示服務網址，形式像 https://<worker_name>.<你的子網域>.workers.dev（帳戶第一次使用 workers.dev 時，可能請你先選一個自己的子網域）。Agent 執行：把網址填入 設定.json 的 origin（只填 https://主機名稱，結尾不加斜線），再做一次：

node tools\prepare.mjs
node tools\deploy.mjs

首次部署時 origin 還是空白，服務只開放首頁、/privacy、/health；填好 origin 重新部署後，私人路由才會開啟。本人操作：瀏覽器開啟服務網址與「服務網址/privacy」，兩頁都要能打開；這兩個網址第 3 步要填進 Google。

簽章密鑰 SIGNING_SECRET

node tools\signing-secret.mjs         # 對外：本機產生（Windows 加密保存），經 stdin 管道安裝到 Worker

你只會看到「已產生」「已安裝」，不會看到密鑰本身。重跑不會換掉既有密鑰；只有加 --rotate 才會換新（舊信勾選與未用的連結碼會失效）。

第 3 步　Google 寄信與日曆事件授權

具備已授權瀏覽器工具時，由 agent 協助導航及一般表單；沒有工具時由本人操作。服務條款、帳單及其他同意畫面由本人處理。

帳號授權範圍用途
專用寄件 Gmail（sender）完整 Gmail 權限 https://mail.google.com/（Google 對 SMTP 的要求）只用來寄出總覽
主帳號（recipient）日曆事件讀寫 calendar.events只管理設定中的一本日曆；先提案、本人確認後新增或改期，不刪除

建立 Google 應用程式

  1. Agent 協助：有授權瀏覽器工具時可協助，否則本人操作。Google Cloud Console → 新增專案（名稱可取「AI 秘書」）。確認上方選到這個專案，在 API 程式庫分別啟用 Gmail API 與 Google Calendar API。把專案 ID（不是名稱、不是編號）填入 google_project_id。
  2. Agent 協助：有授權瀏覽器工具時可協助，否則本人操作。Google Auth Platform → 品牌：應用程式名稱、你自己的支援信箱與聯絡信箱；應用程式首頁填你的服務網址，隱私權政策填「服務網址/privacy」。不要照抄圖解截圖或範例中的網址。
  3. Agent 協助：有授權瀏覽器工具時可協助，否則本人操作。目標對象（Audience，舊介面可能叫「受眾」）：使用者類型選「外部」。發布狀態是「測試中」時，把寄件帳號與主帳號都加入測試使用者。要不要轉正式版，先看下面「發布狀態與 7 天」。
  4. 本人操作：用戶端 → 建立 OAuth 用戶端，類型選網頁應用程式，授權重新導向網址完整填入： 
    http://localhost:8766/oauth/callback
    建立後下載 JSON，留在自己的電腦。

Agent 執行：

node tools\prepare.mjs
node tools\import-google-client.mjs "C:\Users\你的使用者名稱\Downloads\下載的檔名.json"

工具會核對專案 ID、類型與回呼網址；通過後以 Windows 加密保存，不列印內容。匯入成功後可把下載的 JSON 刪除或移到安全位置。

發布狀態與 7 天（先決定）

Google 官方說明：使用者類型「外部」且發布狀態「測試中」的專案，取得的 refresh token 7 天後失效；只要求姓名、電子郵件、基本資料的應用程式才例外，本教材的 Gmail 與 Calendar 不在例外內。（Google OAuth 2.0 說明）
  • 只想先試：保持測試中即可，但約 7 天後寄信與日曆會停止，需要轉正式並重新授權。
  • 要長期使用：目標對象 → 發布應用程式（Publish app），從「測試中」改為「正式版」（In production）。確定要長用的話，可以在下面授權之前就轉，省一次重新授權；若已在測試中授權，轉正式後照附錄 B 重新授權兩個帳號。

詳細說明（未驗證警告、100 人以下的自用例外、權杖仍可能失效的情況）見附錄 B。

先授權專用寄件 Gmail

node tools\authorize.mjs --smtp

本人操作：瀏覽器開啟 http://localhost:8766/start，登入專用寄件 Gmail。若出現「Google 尚未驗證這個應用程式」，先確認畫面上是你自己建立的應用程式名稱，才點「進階」繼續。成功頁出現後，助手會回報已加密保存。

完整 Gmail 權限能讀取、傳送與永久刪除該信箱的郵件；程式實際只核對帳號與寄信。這就是要用「專用寄件 Gmail」、不用主帳號的原因。若帳號政策禁止這項授權，先處理帳號或政策，不要略過錯誤。

再授權主帳號的日曆（事件讀寫）

第一個流程完成後，才啟動第二個（兩個會搶同一個本機埠）。

node tools\authorize.mjs --calendar

本人操作：再開 http://localhost:8766/start，這次改登入主帳號。範圍只有日曆事件讀寫。

兩個授權都會核對 Google 回報的「實際帳號」：登入錯帳號時不會保存任何憑證，會顯示「帳號不符」。已經有授權時也不會被覆蓋；要重新授權需加 --replace。

安裝到自己的 Worker

node tools\install-secrets.mjs        # 對外：經 stdin 管道安裝 6 個秘密
node tools\admin.mjs status           # 核對狀態（不含秘密）

status 裡 mail_credentials_installed、mail_accounts_match_settings、calendar_connected 都應該是 true，schedule_enabled 仍是 false。

第 5 步　開啟 Gmail 動態郵件

  1. 本人操作：用電腦開主帳號的 Gmail 網頁 → 齒輪 → 查看所有設定 → 一般 → 動態郵件：勾選啟用。

第 7 步　日常使用，最後取消兩筆示範

每天怎麼用

  • 一件活動一個聊天（工作模式、選「AI 秘書」專案與「AI 秘書進度」外掛）。交辦三件事：活動、下一步、期限；日期不明時讓秘書先問清楚。

  • 延期、取消、完成都要保存並讀回；也可以直接在信裡勾選，兩邊最後應看到同一個狀態。

附錄 B　Google 發布狀態與長期使用

  • 測試中＝7 天：外部＋測試中的專案，含 Gmail、Calendar 範圍的 refresh token 7 天後失效（Google OAuth 2.0 說明）。
  • 轉正式版：Google Auth Platform → 目標對象 → 發布應用程式，狀態改為「正式版」。如果你在測試中時已經授權過，轉正式後請重新授權並重裝： 
    node tools\authorize.mjs --smtp --replace       （登入專用寄件 Gmail）
node tools\authorize.mjs --calendar --replace   （登入主帳號）
node tools\install-secrets.mjs --only smtp,calendar
node tools\admin.mjs status
  • 未驗證警告與費用：正式版的自用程式，授權時可能看到「Google 尚未驗證這個應用程式」。Google 對自用、使用者少於 100 人的情況列有驗證例外（Google Cloud 說明），所以不是每個人都必須做昂貴的驗證或安全評估。但這個例外不會讓測試中的權杖變成永久，也不保證畫面不出現其他要求；請以你看到的 Google 實際提示為準。
  • 沒有「永不失效」：即使是正式版，Google 文件也列出權杖會失效的情況，例如你撤銷授權、長時間未使用、含 Gmail 範圍的帳號變更密碼、管理員限制等。失效時照附錄 A 重新授權即可，進度資料不受影響。

附錄 G　安全設計與未驗證項目

安全設計

  • 固定帳號防護保留：寄信前比對 Worker 上的寄件／收件與設定；授權時比對 Google 回報的實際帳號；安裝秘密前比對帳號、範圍、用戶端與專案；勾選請求只接受設定的寄件者。
  • 未設定即拒絕：佔位設定、首次部署（尚無 origin）或部署變數與設定不符時，寄信、勾選、MCP、OAuth、管理請求一律拒絕，排程也不寄。
  • 秘密只走加密儲存與管道：本機用 Windows DPAPI，安裝時經 stdin 交給 wrangler secret put，不出現在命令參數或輸出。一次性連結碼只放本機剪貼簿。
  • 每日寄信需明確啟用：預設關閉；啟用需要相符的驗收紀錄與本人確認；帳號欄位一改就自動關閉。
  • 不重寄：每日信與驗收信各以日期去重；結果不確定時不自動重寄。
  • 示範清理有範圍：cancel-demo 只處理指定 ID，先全部檢查再變更，不會把已完成改回 pending，也不是刪除。

這份附檔沒有、也不能替你驗證的事

  • 沒有在任何新的 Cloudflare 或 Google 帳戶上用這份複本實際部署或授權；離線測試只用虛構資料。
  • Wrangler 4.141.0 的實際安裝、登入、d1 execute --remote、secret put 經管道輸入、triggers.crons 的雲端行為，需要在你的帳戶實際執行時確認。
  • Google OAuth 政策、Gmail 動態郵件在你的帳戶與手機上的顯示。
  • ChatGPT 自訂 MCP 外掛、預設記憶專案與工作模式是否對你的帳號開放。
